Recurring Payments Audit

How recurring payments actually work in Hacienda, how they reach Expenses and the Dashboard, and where the implementation diverges from the model the brief assumes. Every claim below was read out of the code, not inferred from naming.

Scope Recurring · Expenses · Dashboard Read 14 source files, 17 migrations Date 15 October 2026 Schema changes none Status 4 of 6 defects fixed
Headline

There is no recurring-payment rule

is_recurring is a boolean column on transactions. The Recurring screen is a derived view that loads flagged transactions and groups them by description. Everything else follows from that one fact.

0 Rule entities No table, no row, no identity. A series exists only as transactions sharing a description.
1 Next-date engine The Recurring screen, the notification bell and the Dashboard now read one schedule. Two predictNext copies are gone.
1 Record type Only a transaction row carries money, so obligations cannot be double-counted.
2 Defects still open Of six found, four are fixed. The two that remain are limits of the model itself, not coding errors.
Lifecycle

The arrow of causality runs backwards

The brief describes obligations flowing forward into expenses. Hacienda infers obligations backwards out of expenses that already happened. Both chains end at the Dashboard, but only one of them can schedule a bill you have never paid.

Model assumed by the brief

Not implemented
Recurring rule → Scheduled occurrence → Expense transaction → Payment confirmation → Dashboard

Three of the five stages have no record behind them. scheduled_payments exists in 001_schema.sql and would fit the first two — but no frontend code reads or writes it.

What Hacienda actually does

Verified
Expense transaction → Flagged is_recurring → Series inferred by description → Occurrence projected → Status derived → Dashboard

The transaction is the source, not the output. Nothing is generated, scheduled or written ahead of time — the projection lives in memory only.

FR-01

Eight questions, answered from the code

QuestionWhat the implementation does
Create Recurring.jsx calls addTransaction({…, is_recurring: true}). This writes one transaction — an expense that has already happened — not a rule.
Edit Opens the standard transaction modal and updates that single row. There are no future occurrences to update, because none exist as records.
Pause / resume Absent No is_active field, no status, no UI. A series can only be unflagged or deleted.
Delete “Remove from recurring” sets is_recurring = false on one row — see defect 1. Deleting the transaction removes history as well.
Frequency Never declared. detectFrequency() takes the median gap between observed dates and snaps it to the nearest of 7, 14, 15, 30, 91 or 365 days. A one-transaction series defaults to Monthly.
Next payment date One implementation, in paymentSchedule.js, stepping by calendar month so day-of-month survives short months and year boundaries. Previously three — see defect 3.
Auto-generates expenses? No — and this is correct No cron, no trigger, no insert path. The flag is retrospective. 015_auto_categorize_trigger.sql only assigns categories.
Paid / partial / outstanding Derived by matching real transactions against projected occurrences, and now reported the same way on the Dashboard, the Recurring screen and the notification bell.
Profile & family Via transactions.user_id plus a person label. RLS grants household-wide SELECT and own-only writes. Every surface now honours the profile selector.
FR-02 · Critical requirement

Double counting cannot happen

Verified, with the reason. Hacienda has exactly one record type that carries money: a transactions row. Expenses, Reports, Budgets and the Dashboard's income and expense figures all read that same row once. An “obligation” exists only as an in-memory projection in paymentSchedule.js, and it is never added to any financial total — the Upcoming Payments card's Scheduled and Outstanding figures are deliberately separate from the Income and Expenses figures above it.

The flip side is that the system holds only two of the three concepts the brief asks it to distinguish. It has actual expenses and derived obligations. It has no record of a payment applied to an obligation — which is why “Paid” has to be inferred by matching amounts rather than confirmed outright.

Findings

Defects, ranked by impact

Ranking is the structure here: 1 and 2 affected daily use, 3 and 4 made modules disagree — all four are now fixed. 5 and 6 are limits of the model itself and need the obligations rethink below.

1

Removing a series unflagged only one transaction

Fixed

removeRecurring(id) updated a single row, and the Recurring screen passed the group's representative — the newest transaction. The other occurrences kept is_recurring = true, so the series reappeared on refresh behind an older representative, and clearing a year of a monthly bill took twelve clicks. It now takes the grouped item and unflags every transaction in it.

frontend/src/hooks/useRecurring.js · frontend/src/screens/Recurring.jsx

2

The Recurring screen ignored the profile selector

Fixed

It called useRecurring() with no argument, so userId stayed null and the query returned the whole household — in Personal mode you saw the other member's obligations. It now scopes the same way Transactions, Expenses, Calendar and the Dashboard already do — as does the notification bell, fixed alongside defect 3.

frontend/src/screens/Recurring.jsx

3

Three different next-date calculations

Fixed

The Recurring screen used predictNext() — last date plus N days — and the notification bell carried its own copy, while the Dashboard stepped by calendar month. Day-stepping drifts: a bill due 31 January landed on 2 March instead of 28 February, and the drift compounded every cycle. useRecurring now owns the projection and hands the same schedule to every surface; both predictNext copies are deleted.

useRecurring.js · useNotifications.js · lib/paymentSchedule.js

4

“Overdue” on the Recurring screen ignored payment status

Fixed

The badge was computed purely from the predicted date, with no reference to whether money moved, so a bill paid on time read as Overdue while the Dashboard correctly read it as Paid. The bell shared the flaw, merged members, and ignored the profile selector. Both now report the real occurrence — Paid, Partially paid, Overdue, Due today or Upcoming — and the bell stays silent on anything already settled.

frontend/src/screens/Recurring.jsx · frontend/src/hooks/useNotifications.js

5

An obligation is invisible until its first payment

Structural

Because the series is inferred from transactions, a bill you have never paid cannot be scheduled, and a cancelled subscription keeps projecting forward until it is unflagged. This is a direct consequence of the backwards lifecycle, not a coding error.

6

The description is the series identity

Structural

Grouping keys on lowercased description plus owner. Renaming one transaction silently splits a series in two; renaming two unrelated bills alike silently merges them. A variable bill such as hydro also reads as Partially paid whenever it lands more than 2% below its median.

Verified

What is working correctly

✓ No duplicated financial records. One record type, read once by every total.
✓ Obligations stay out of expense totals. Scheduled and Outstanding never enter Income or Expenses.
✓ Permissions hold. Household-wide SELECT, own-only INSERT/UPDATE/DELETE, unchanged.
✓ Currency conversion is centralised. toBase() and buildRateMap() carry the default-rate fallback; nothing sums CAD and COP raw.
✓ Ownership resolves once. A shared bill belongs to the member who pays it and is counted a single time.
✓ Period and status stay independent. An unpaid October bill remains filed under October once November starts.
Delivered

What changed

The Dashboard accordion, plus the two defect fixes. No scheduling or expense calculation was altered, and no migration was added.

One rule worth knowing. Grouping always runs over every occurrence, so month and member totals describe the whole period. The Outstanding / All toggle decides which rows are listed — it never changes what a period says is owed. A collapsed section therefore still reports the truth, which is what makes the summaries usable without expanding anything.
Next

Recommendations

Ordered by how much each one unblocks. The first two close defects; the rest change the model.

Fix defects 1 and 2 Done

The whole series is now unflagged rather than one row, and the Recurring screen passes the profile into useRecurring(). Neither needed a schema change.

One scheduling engine Done

useRecurring builds the schedule once and exposes it, so the Recurring screen, the notification bell and the Dashboard all read the same projection. Both predictNext copies are deleted. This closed defects 3 and 4 together.

Declare obligations

scheduled_payments already has name, amount, frequency, next date and is_active. Adopting it gives real rules, a pause switch, exact expected amounts, and bills that can be scheduled before they are first paid.

Record the application

A link from a transaction to the occurrence it settles turns “Paid” from an inference into a fact, and makes partial payments explicit instead of implied by a shortfall.

Give a series a stable id

Once rules exist, point transactions at the rule instead of matching on description. Renaming a bill stops splitting its history.

Split shared obligations

person = 'Shared' marks a bill as shared but does not model who owes what share of it. Family subtotals currently attribute it wholly to its payer.

Open

Outstanding issues

  • Defects 1 through 4 are fixed and covered by tests. Defects 5 and 6 remain: they are consequences of inferring obligations from transactions, and closing them means adopting real obligation records rather than patching the derivation.
  • 16 Playwright tests across status-badge, transfer-pairs and the verify-* specs fail. Four need a PW_PASSWORD that is blank in .env.test; the rest rely on stale fixtures. Confirmed identical on a clean baseline, so none are caused by this work.
  • Member subtotals describe the whole period while the Outstanding filter hides settled rows. Intended, and the toggle sits directly above — but it is the one place a reader may need a second look.
